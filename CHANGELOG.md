# Changelog

Every user-visible change, by version. The plan for the versions ahead is in [docs/versions.md](docs/versions.md).

## Unreleased

### Added
- **`∧/` and `∨/`, the and and or reductions** (`all` and `any` written as glyphs, as in APL): `same ▷ ∧/`, `∨/ flags`.
- **`math::tanh`, `math::sinh`, `math::cosh`, `math::log1p`, `math::expm1` and `math::sigmoid`** (libm calls that fuse into array kernels like `math::exp`; `log1p` and `expm1` exact near zero; `sigmoid` without overflow for large negative inputs), and **`unwrap_or`** for an `Option`: `parse_int(s) ▷ unwrap_or(300)`. Reported by a user.

### Changed
- **A pure `¨` over a short list runs on one core unless its elements are worth sharing out:** up to 16,384 elements, a function's first such `¨` is shared out as before while its cost per element is timed, and later ones go to the other cores only when that cost pays for waking them (else they run on one core, timed as they go). A sudoku check of 20,000 grids ran 6× slower on 12 cores than on one (about 4 s, mostly in the kernel); it now takes 0.7 s.
- **Reads of a list are made before the changes that follow its copy:** `let mut s = h` then `s[i] = h[j]` `s[j] = h[i]` (a swap), and `f(push(h, v), ≢ h)`, now change `h` in place instead of copying it at every step; a heap's 20,000 pushes took 1.75 GB, now 2 MB.
- **A function whose last act is calling itself runs as a loop, however deep, in release and debug builds:** what the call no longer needs (its locals, a string built on the way, a tuple's parts, a list copied with `let mut v = xs` and changed) is released or handed over before the call, so the call becomes a jump. Recursions a million calls deep over lists, strings and records used to overflow the stack and stop with a segmentation fault; 11 of the 12 held-out programs that did now finish (`sudokucheck` no longer crashes but is slow).
- **A list of any element type grown by `push` (or changed by `put` or `concat`) where it is used for the last time is changed in place**, strings, floats, records and maps included: `gen(n - 1, y, push(acc, v))` hands the same list down the recursion instead of copying it at every step (before, only lists of `i64` were, so building a list of strings this way took time and memory growing with the square of its length). A map threaded through a recursion with `put` is changed in place too. Found by the held-out set (BENCHMARK.md): most of its programs build their input this way.
- **A parameter declared as a list of numbers (`xs: [i64]`, `[f64]`) is that list:** given a list of unknown type (`[]`, the result of `flatten`, a list grown from `[]`), the function used to be compiled for the unknown type, on the generic path, and the declaration only checked; now it is compiled for the declared type and the call converts the list (a list already of that type is passed as it is). `bigfactorial` in the held-out set (a list of digits started as `[]`): 39 s → 0.9 s. Reported by a user too (`bytes: [i64]` showing as `[?]`).

### Fixed
- `mimic fmt` (and formatting from an editor or the MCP server) leaves a file that does not parse untouched and reports the parse error; `fmt --glyphs` had rewritten `∧/` into `∧÷`.
- **A primitive's word is refused wherever a name is declared (E0214):** a parameter or a typed `let` named `shape` (the word of `⍴`) was accepted, then every use of it was the primitive, with a misleading parse error (`expected an expression, found '=='`). Functions, parameters, `let`s and lambda parameters now all give E0214 naming the primitive. Reported by a user.
- **A function named like a built-in primitive is refused (E0214):** `fn matmul(…)` compiled, but every `matmul(…)` elsewhere is the primitive `⊠`, so the function could never be called and nothing said so. It is now an error where the function is declared, naming the primitive. (C functions keep such names under `c::`.)
- **Stopping `mimic run` stops the program:** on macOS and Linux the program now takes the place of `mimic run` instead of running as its child, so `kill`, a time limit or a closed terminal ends the program itself (before, only `mimic` stopped and the program kept running, holding its memory), and the shell sees the program's own exit status.

## 0.4.2 — 2026-11-24

Step 0.4.2, ownership by analysis: in the functions the Mimic IR compiles, a list or record is released right after its last use, handed over instead of shared, and changed in place wherever nothing else holds it, through helper calls, record updates and branches, in debug builds as in optimised ones. Text and functions that call several others now go through the IR too, numbers and literals that live for the whole run are never counted, and operators on values of unknown type no longer allocate their results. Reference-count operations over the corpus fell by 40% (937 million to 563 million, short of the halving the plan aimed at; what is left is mostly in code the IR does not cover yet). `mimic check --copies` lists the copies a program still makes and why: `paths`' step makes none; `qoi`'s steps are still compiled by the old code generator (they wait for typed empty lists and tuples holding lists, 0.4.3–0.4.4). `sudoku` 1.9× faster, `vm` 1.7×, `tokenize` 1.5×, `totient` 1.3×, `paths` 1.27×, `hull` 1.2×, `lz77` 1.18× on this machine; the whole corpus on Linux, macOS and Windows is in BENCHMARK.md.

### Added
- **`mimic check --copies`** lists every copy of a list or record the program still makes, where, and why: a `put`, `push` or `{ … with … }` on a value used again later (and at which line), read from outside a loop, or borrowed from the caller. Functions the compiler does not analyse yet are listed with the reason. `--emit-json` gives the same as JSON.

### Changed
- **A step function takes its record state wherever it hands it on or updates it last:** a record parameter read first (`let p = ps[s.i]`, `s.v[i]`) and then passed to a function that changes it, or used as the base of a `{ … with … }`, is now taken over, so the change is made in place instead of on a copy: `look(look(s, 0), 1)`, `{ grow(t, at) with k: t.k + 1 }`, `let e = learn(d, c)` after `codes[d.i]`. And a field changed in one branch and kept in the other (`next: if d == 0 { push(k.next, w) } else { k.next }`) is two updates, the one taken in place. These shapes took minutes in 0.4.0 (docs/gaps.md); the corpus already avoids them.
- **A list field changed under a `let` and stored back is changed in place:** `let table = put(s.table, h, x)` then `{ s with table: table }` copied the whole list (the record still held it when the `put` ran); the change now happens in the `with`, which takes the field out of the record, so it is made in place when nothing else holds them. The same for chains of `put` and `push`, and `{ s with out: concat(s.out, ys) }` now appends in place in the functions the IR compiles. `lz77` is 15% faster (its table of 65,536 entries was copied for every byte).
- **Values are released as soon as they are last used, and handed over instead of shared** (docs/design/ownership.md): in the functions the IR covers, a list or record is freed right after its last use (not at the end of its block), given as it is to a function that takes it over, and stored into a record without a new reference. A field read borrows its record. Records on the heap, `{ r with … }` and functions that take over a record argument now go through the IR; `floyd` is 1.26× faster.
- **`put` and `push` on a list of `i64` change it in place when nothing else holds it:** a list the function owns at its last use (`let g = push(h, x)`, `put(put(h, p, b), i, a)`) is changed where it is, and `{ s with v: put(s.v, i, x) }` stores the number in place without a call. A function whose list parameter is changed this way at its last use (a heap's sift-up `up(put(put(h, p, b), i, a), p)`), or handed on to one that is, now takes the list from its caller, so the change is in place there too. Before, a bare `put` always copied the list.
- **Releasing a number, `true`, `false` or a literal no longer calls the runtime:** these values live for the whole run, and compiled code now skips them where it releases a value. They were half or more of all reference-count operations in `vm`, `soundex` and `url`; `vm` is about 4% faster.
- **Text, and functions that call several others, now go through the IR:** functions that take or return strings, and blocks with more than one call (only blocks the compiler would actually run in parallel, or start as a task, stay on the old path), now get release-at-last-use and in-place updates. `sudoku` is 1.9× faster, `paths` 1.27×; `put`/`push` on a list a function only borrows copies it directly instead of taking a reference first. `MIMIC_IR=why` prints why a function stays on the old path.
- **Comparing or computing with two numbers of unknown type no longer allocates:** an operator on two single values whose type the compiler does not know (`op == 0` in an interpreter's loop) gave a new value every time; a truth value or an integer from such an operator, and from `not`, `-` and `∣` on one value, is now the runtime's own `true`/`false` or cached small integer. `vm` is 1.7× faster (8× fewer values freed), `tokenize` 1.5×, `brainf` 6% faster.

## 0.4.1 — 2026-11-22

Step 0.4.1, the Mimic IR: programs are now compiled through a typed intermediate representation between the syntax tree and LLVM, on by default, with fusion as a pass over it. Array code computed element by element (`⍳ n`, operators on lists, `xs ¨ f`, reductions) is fused by the IR, across `let`s and small helpers it inlines; what the IR does not cover yet is compiled by the old code generator where it stands, until that is retired (0.4.10). Also a security fix for the HTTP client's redirects, and the slowest benchmarks of 0.4.0 traced and most of them made several times faster without a change to the programs: tuples of numbers and short lists stay in registers, lists grown in a loop and lists from `flatten` stay typed, `let` lambdas and `count`'s lambda are compiled as functions, `gather`/`trail` with a lambda are typed loops, and debug builds change lists in place. `fnv1a`, `crc32`, `adler32`, `pagerank`, `topo` and `siphash` 7–25× faster, `sha256` 13×, `diff` 7×, `utf8` 5.6×; no benchmark slower on Linux, macOS or Windows.

### Added
- **The Mimic IR** (docs/design/ir.md): a typed intermediate representation (SSA, with structured control flow) between the syntax tree and LLVM, with passes over it: fusion, sinking (work moved into the one branch that needs it) and inlining of small helpers. `MIMIC_IR=print` shows each function's IR, `MIMIC_IR_ONLY=text` sends only the functions whose path holds `text` through it.

### Security
- **The HTTP client keeps credentials to the server they were meant for.** A redirect from `https` to `http` is refused with an `Err` (the request would go on unencrypted), and a redirect to another server (a different scheme, host or port) leaves `Authorization`, `Cookie` and `Proxy-Authorization` behind; other headers still go along. Before, `http::request` sent them on to wherever it was redirected.

### Changed
- **Programs are compiled through the Mimic IR:** the functions it covers (numbers, values kept in registers, loops, `match`, lists read and owned, reductions, lists computed element by element) go through it, and what it does not cover yet is compiled by the old path where it stands. The same output and speed; `MIMIC_IR=0` turns it off.
- **Fusion is decided by the IR:** a list computed element by element and read once by a later computation is never built (`let ys = xs × 3`, `let zs = ys + xs`, `zs ▷ +/` is one loop), nor is a small one read several times (computed again where it is read); `xs ¨ f` takes part, and so does a small helper, inlined first (`fn sq(xs) { xs × xs }` then `sq(v) ▷ +/` is one loop).
- **`+/ ×/ ⌈/ ⌊/` of a list of numbers is the fused engine's kernel** (SIMD, split over the cores) instead of the runtime's generic call, its result unboxed.
- **Lists grown in a loop stay typed:** `push` of a number onto a list of that kind of number gives such a list, a loop whose list state changes length (`⍳ 16` grown to 64 by `push`) keeps it typed, and a tuple holding short lists of known length (`(i, [8 words])`) stays in registers. `sha256` 13× faster (4.7 s → 0.35 s).
- **A function declared `-> [i64]` (or `[f64]`) returns a typed list:** a body joining `[]` with `[x]` gave a list of unknown type, which the declaration only checked, so the caller worked on boxed values. The result is now made typed as it is returned. `diff` 7× faster (3.8 s → 0.54 s). A function that returns something else under such a declaration now stops at its return instead of later.
- **`flatten(xs ¨ (x => …))` of lists of numbers is typed:** its result had no known type, so everything after it ran on the generic path; when the lambda gives a list of numbers, the result is that list of numbers. `utf8` 5.6× faster (4.0 s → 0.71 s).
- **`gather` and `trail` with a lambda over numbers are a typed loop:** `ways ▷ gather((x, y) => (x + y) % p)` sent every pair through the runtime boxed; a lambda that gives back the same kind of number as the list's is now typed and folded in a loop. 3,000,000 numbers: 2.35 s → 0.08 s. A lambda giving another type keeps the general path.
- **`count(xs, x => …)` is typed and fused:** the prelude's `count` called its lambda as a function value for every element; given a lambda, the call is now written out as its body, `+/ (xs ¨ (x => …))`. `maze` 5× and `markdown` 1.2× faster.
- **A list of literals is built once:** `["M" "CM" "D" …]` or `[1 2 3 …]` in a function was built again on every call; it is now built the first time and shared after (a change to it copies, as to any list held twice). `roman` 2.1× faster (3.2 s → 1.5 s of CPU).
- **A lambda kept in a `let` and only called is a function:** `let at = (x, y) => table[…]`, then `at(a, b)`, called the lambda as a function value, every argument boxed; it now becomes a hidden function taking what it captures as arguments, specialised like any function. 8 million calls in a map: 5.8 s → 0.03 s. A lambda used as a value, or one that assigns, returns or sees a variable that changes later, stays as it was.
- **Tuples of numbers stay in registers:** a `settle` or `evolve` over a tuple state (a sequential pass, a hash, a binary search) allocated and freed a tuple on every step; a tuple of numbers and truth values is now kept in registers, as records of numbers are. `crc32` 6.8 s → 0.79 s, `fnv1a` 4.5 s → 0.62 s, `topo` 5.1 s → 0.79 s (one core, macOS).
- **Small programs build faster:** a one-line program in about 0.45 s instead of 0.6 s on macOS. The linker runs inside `mimic` instead of as a second process (which took ~0.1 s just to start), and the macOS SDK and OS version are read from their files instead of asking `xcrun` and `sw_vers` on every build (~70 ms). `MIMIC_DEBUG_PHASES=1` also times code generation, the runtime and linking.

### Fixed
- **`push` onto a short list no longer reallocates every time:** a list that had grown past its first block kept asking `realloc` for more room on each `push`, though it had plenty. `levenshtein` (rows built a number at a time) runs 2.5× faster on macOS, more on Windows.
- **`MIMIC_IR` and `MIMIC_DEBUG_DISABLE` are part of the build cache's key:** a program built with one of them could be reused by a build without it (and the other way round).
- **A redirect to `//host/path` goes to that host** with the request's scheme; it was taken as a path on the same server. A `Location` too long to follow is an `Err` instead of a cut-short URL.
- **Debug builds update records in place, as optimised ones do:** `{ s with f: put(s.f, …) }` copied the whole list on every step in a debug build (functions never took over their parameters there). A debug sieve of 200,000 took over ten minutes; now 1.8 s.
- **A program with only small maps no longer opens Metal on macOS:** the GPU was asked before the map's size was checked, and asking opens Metal (~0.13 s). A program over 1,000 numbers ran in 0.14 s; now 0.01 s. Large maps go to the GPU as before.

## 0.4.0 — 2026-11-20

Stage 0.4.0, the measuring stick: a benchmark corpus of 130 everyday algorithms (hashing, parsing, graphs, text, interpreters, compression, numbers, simulations, geometry, images, data structures and dynamic programming), each in Mimic, C and Rust and checked against an independent reference; the machine's limits; and a speed gate on Linux, macOS and Windows that fails CI on a slowdown. The corpus found the bugs and slow paths fixed below, and the gaps left for the rest of stage 0.4 (docs/gaps.md). Its algorithms also became standard modules: `hash`, `text`, `graph`, `order`, `parse`, `compress`, and whole numbers in `math`.

### Changed
- **The standard library's own records hold raw numbers,** as a program's do: its private helper records (the state of `hash`, `graph`, `compress`, `math::primes` …) kept every number boxed, so their loops ran 2–15× slower than the same code in a program (`math::primes(10000000)`: 5.0 s → 0.35 s; `compress::rle` of 4 MB: 1.2 s → 0.15 s). Public types, which the runtime builds too, keep their layout.
- **`sieve` and `kmeans` are written as one would write them:** `sieve` keeps its flags in bytes, as C does, and `kmeans` passes its centres as a record. Both workarounds are gone now that `put` on bytes is in place and a record passed along a recursion is borrowed.
- **The speed gate times short benchmarks longer:** each side runs until it has run for a second (at most 30 runs) before the best time is taken. Benchmarks of 50–130 ms raised false alarms of 6–22% with the best of 3.
- **The gate's noise is measured as the gate compares:** `bench/run.py --noise` now runs the gate's comparison with the same compiler on both sides; a benchmark too noisy for the 25% limit on a platform is reported there, not gated. (The first noise data, ratios to C across whole rounds, overstated it, and a preview's identical compiler failed the gate on `tree` and `ui`.)
- **Benchmarks against C and Rust only:** the Go versions are gone, from the suite and from the tables in BENCHMARK.md and on the website. The http benchmark's load generator is now a Rust program (`bench/http/load/main.rs`).

### Added
- **Whole numbers in `math`, from the corpus:** `math::gcd`, `lcm`, `powmod` and `mulmod` (exact for any `i64`, with 128-bit products), `is_prime` (Miller-Rabin, exact for every `i64`), `primes` (a sieve) and `totient`, checked against Python and sympy. Golden test `math_whole`, docs/std.md and the tutorial.
- **`compress`, from the corpus:** `compress::rle`/`unrle`, `compress::lzw`/`unlzw` (12-bit codes) and `compress::varints`/`unvarints` (zigzag LEB128 deltas), checked against reference implementations in Python, with every round trip and each decoder's `Err` for input it did not make. Golden test `compress_module`, docs/std.md, the tutorial (chapter 16) and man pages.
- **`order` and `parse`, from the corpus:** `order::lower_bound`, `upper_bound`, `select` (quickselect) and `merge`, checked against Python's `bisect` and `sorted`; `parse::csv` (RFC 4180, against Python's `csv`), `parse::url` (against `urllib.parse.urlsplit`) and `parse::semver` with `semver_compare` (against the precedence chain of semver.org). Golden test `order_parse`, docs/std.md, the tutorial (chapter 6) and man pages.
- **`graph`, from the corpus:** `graph::bfs`, `graph::shortest` (Dijkstra with a binary heap), `graph::components` (union-find), `graph::topo` (Kahn's algorithm, `None` for a cycle) and `graph::mst` (Kruskal), on nodes 0 … n - 1 and edges as lists, checked against networkx on graphs of up to 20,000 nodes. Golden test `graph_module`, docs/std.md, the tutorial (chapter 6) and man pages.
- **`text`, from the corpus:** `text::distance` (Levenshtein, by characters), `text::find_all` (every occurrence, overlapping, by KMP), `text::soundex` and `text::wrap` (greedy, as Python's `textwrap`), checked against Python and Soundex's published examples. Every loop is a loop in debug builds too, so a pattern that falls back far or a long name cannot exhaust the stack. Golden test `text_module`, docs/std.md, the tutorial (chapter 6) and man pages.
- **`hash`, the first module graduated from the corpus:** `hash::crc32`, `crc64`, `adler32`, `fnv1a32`, `fnv1a64`, `murmur3`, `xxhash32`, `xxhash64`, `siphash`, `md5`, `sha1` and `sha256` on bytes, checked at every length around their block sizes against Python's `zlib`, `hashlib`, `xxhash` and `mmh3` and the published test vectors, in optimised and debug builds alike. Byte-by-byte loops run in chunks, so a debug build hashes any size without running out of stack, and an optimised one as fast as the benchmark's loop. Golden test `hash_module`, a section in docs/std.md and the tutorial (chapter 16), and man pages (`mimic man hash`).
- **The corpus reaches 130:** 41 more everyday algorithms in Mimic, C and Rust, each checked against an independent reference: numbers (`gauss`, `millerrabin`, `coprime`, `totient`, `partitions`, `fibmod`, `catalan`, `polyeval`, `bigfact`), simulations (`shuffle`, `randwalk`, `ising`, `sandpile`, `rule110`, `traffic`, `langton`), puzzles (`tsp`, `sudoku`, `knight`, `matchain`), graphs (`mst`, `bellman`, `bipartite`, `flood`, `maze`), data structures (`lru`, `rangemin`, `intervals`, `bitset`), text (`roman`, `soundex`, `wordwrap`, `xmltags`, `markdown`, `template`, `lisp`), hashing and ciphers (`crc64`, `sha1`, `chacha20`), `base32` and `dct`. On one core on the M-series Mac most are within 1-2× of C (`intervals`, `mst`, `bellman`, `ising`, `partitions`, `sha1` and `base32` faster); the slowest are text built piece by piece (`markdown` 4.9×, `xmltags` 4.4×, `soundex` 3.6×, `roman` 3.5×), `tsp` 4.2× (the table rewritten for each set size), `sudoku` 3.8× (a new board for each placement) and `flood` 3.4× (a pair made for each neighbour). Writing them found the fixes above, and gaps recorded in docs/gaps.md.
- **The corpus, more text:** `zalgo` (Z-algorithm), `manacher` (Manacher's palindromes) and `anagram` (anagram classes), in Mimic, C and Rust, checked against Python. On one core on the M-series Mac, against C: `manacher` 1.9×, `zalgo` 3.2× (sequential passes that `put` into a list held by a record: 0.4.3), `anagram` 6.5× (half a million words built letter by letter as strings).
- **The corpus, geometry:** `hull` (convex hull by monotone chain), `pip` (point in polygon by ray casting) and `segments` (segment intersection, all pairs), in Mimic, C and Rust, in exact integer arithmetic, checked against Python. On one core on the M-series Mac, against C: `hull` 0.75× (sorting one number per point), `segments` 1.1×, `pip` 1.3×; on all cores 2.2–4.5× faster than C. Found on the way: `(a > y) != (b > y)` is refused as a chained comparison, and a long condition cannot be split over lines except inside parentheses (docs/gaps.md).
- **The corpus, more parsing, and servers:** `numparse`, `semver` and `ini` (checked against Python, `ini` against `configparser`), and two servers with their own load generators: `http_route` (a JSON API with path parameters and 404s) and `http_echo` (POST bodies answered in upper case), in Mimic, C and Rust (hyper). On one core on the M-series Mac, against C: `http_echo` 0.96×, `http_route` 1.6×, `numparse` 2.4×, `semver` 3.2×, `ini` 4.0× (each `slice` and `trim` makes a new string: docs/gaps.md, 0.4.12); on all cores both servers match or beat the single-threaded C server.
- **The corpus, more compression and hashing:** `varint` (zigzag LEB128 deltas), `bitpack` (13-bit values in 64-bit words), `lzw`, `xxhash64`, `md5` and `siphash` (SipHash-2-4), in Mimic, C and Rust, checked against Python (`xxhash`, `hashlib`, and the SipHash paper's test vector). On one core on the M-series Mac, against C: `bitpack` 1.8×, `md5` 1.4×, `xxhash64` 1.6×, `varint` 3.9×, `lzw` 3.8×, `siphash` 22× (its rounds return the state as a tuple, which is allocated: docs/gaps.md, 0.4.3). `bitpack` packs and unpacks as one parallel map each; the hashes loop with a function that calls itself, which is many times faster than a `settle` over a tuple. Found on the way: deep recursion through a function that takes a list or returns a tuple can still overflow the native stack past ~50,000 levels, with no message (docs/gaps.md); a type name for a tuple is not accepted.
- **The corpus, dynamic programming:** `lcs` (longest common subsequence, each row one map and one `trail(⌈)`), `coins` (ways to make change) and `lis` (longest increasing subsequence by patience sorting), in Mimic, C and Rust, checked against Python. On one core on the M-series Mac, against C: `lis` 0.7×, `lcs` 1.5×, `coins` 4.3× (a step that `put`s into a list held by a record goes through the record each time: docs/gaps.md, 0.4.3). Found on the way: `gather` with a lambda goes through the runtime one boxed pair at a time (docs/gaps.md, 0.4.1).
- **The corpus, sorting and searching:** `radix` (LSD radix sort), `bsearch` (binary search, lower bounds) and `select` (quickselect), in Mimic, C and Rust, checked against numpy. On one core on the M-series Mac, against C: `bsearch` 0.9×, `select` 1.6×, `radix` 4.8× (every `put` of its placing pass is a call into the runtime: docs/gaps.md, 0.4.3). A bottom-up merge sort is written but waits for lists built from pieces to keep their type (docs/gaps.md).
- **The corpus, images:** `histeq` (histogram equalization), `rotate` (90° turns), `dither` (Floyd–Steinberg error diffusion) and `integral` (a summed-area table and 8,000,000 box sums), in Mimic, C and Rust, checked against Python (numpy for all but `dither`). On one core on the M-series Mac, against C: `histeq` 1.7×, `rotate` 1.6×, `dither` 2.2×, `integral` 1.5×; on all cores each is faster than C (frames, rows and boxes run in parallel). Found on the way: a lambda kept in a `let` and called in a hot loop is 15–40× slower than the same named function (docs/gaps.md, for 0.4.1).
- **The corpus, data structures:** `bloom`, `hashmap`, `heap` and `fenwick`, in Mimic, C and Rust, checked against Python. Each updates a list in place step by step (`evolve` with a named step, `put` through a record) and reads it in parallel. On one core on the M-series Mac: `bloom` 1.5× C, `hashmap` 2.1×, `heap` 2.1×, `fenwick` 1.9×. Writing them found `evolve`/`settle` with named functions copying the state at every step (fixed), and a list passed bare to a function that `put`s into it being copied at every `put` (docs/gaps.md).
- **The corpus, puzzles and tables:** `nqueens`, `knapsack`, `floyd` and `collatz`, in Mimic, C and Rust, checked against Python (numpy for `floyd`). On one core on the M-series Mac: `nqueens` 0.9× C (0.53 s on all cores, with the parallel map fix), `knapsack` 2.0×, `floyd` 2.9×, `collatz` 2.4×. Writing them found two gaps (docs/gaps.md): `settle` over a tuple was 25× slower than the same loop as a recursion (`collatz`), and an index computed from `p div n` and `p % n` in every element keeps `floyd` at 2.9× C.
- **The 0.4.0 corpus, text:** `levenshtein`, `kmp`, `utf8`, `aho` (Aho-Corasick), `diff` (Myers), `trie` and `wordfreq`, in Mimic, C and Rust with the same algorithms, checked against Python. Work that splits into independent pieces runs close to C on all cores (`kmp` 1.07×), while one byte or cell at a time stays 22–36× on one core.
- **The 0.4.0 corpus, numbers and simulations:** `sieve`, `montecarlo`, `blackscholes`, `heat`, `life`, `fft`, `kmeans` and `bigmul`, in Mimic, C and Rust with the same algorithms, checked against Python (numpy, or its own big integers). Arithmetic over independent elements is at or near C on one core (`montecarlo` 1.0×, `blackscholes` 1.18×, `kmeans` 0.84×) and several times faster on all cores. Writing them found four gaps (docs/gaps.md): a record used inside `¨` is retained and released for every element (20× the CPU time on all cores), `put` on `[u8]` copies, `math::pi` without `()` passes the checker, and an FFT built from `¨` stages is 6× C.
- **The 0.4.0 corpus, graphs:** `bfs`, `components`, `topo` and `pagerank`, in Mimic, C and Rust with the same algorithms, checked against Python. Writing them found two more ways an update is copied instead of made in place (docs/gaps.md): an `if` inside `{ … with … }` (118 s against 7 s) and a helper that changes an array its caller's record holds.
- **The 0.4.0 corpus, interpreters and regex:** `regex` (a Thompson NFA engine, checked against Python's `re`), `brainf` (a Brainf**k interpreter) and `vm` (a stack bytecode VM), in Mimic, C and Rust. An interpreter's loop is 27–54× C today (docs/gaps.md).
- **The speed gate:** `bench/run.py --gate BEFORE` builds every benchmark with the changed compiler and with the one it changes, times them in turns on the same machine, and fails on a slowdown beyond that benchmark's tolerance (twice its noise measured on GitHub's machines, 3–25%, from `bench/noise/`) in 2 of 3 measurements. The bench workflow runs it on release pull requests, nightly on `dev`, and on pull requests that change what is measured, and checks each time that the compiler without its optimizer (`MIMIC_DEBUG_DISABLE=optimizer`) fails it.
- **The 0.4.0 corpus, hashing:** `crc32`, `adler32`, `fnv1a`, `murmur3`, `xxhash32` and `sha256` benchmarks in Mimic, C and Rust, checked against independent references. They show sequential passes over arrays 13–57× slower than C and SHA-256 170× (docs/gaps.md, with the 0.4 steps that fix them), and that Mimic has no `fold`.
- **The 0.4.0 corpus, parsing:** `csv`, `expr`, `tokenize`, `url` and `http_parse`, checked against Python's `csv`, `eval`, `re` and `urllib`. Parsing that splits into independent pieces runs in parallel and is at or near C's time on all cores (`csv` 0.90×, `expr` 0.95×); scanning characters one at a time is 25× C on one core (docs/gaps.md).
- **The 0.4.0 corpus, compression:** `rle`, `base64` and `lz77`, checked against Python (`base64`, and reference implementations). They show where growing a list in a loop copies it: the LZ77 decoder is 476× C (docs/gaps.md). `rle` found `flatten` quadratic (fixed above). `huffman` and `bwt` follow: `huffman` showed a `settle` step written as a lambda copying its state where a named step function changes it in place (37 s against 2.1 s).
- **The share of the machine:** `bench/machine/` measures the peak floating-point rate and the memory bandwidth, on one core and on all, and benchmarks that declare their work (`meta.json`: matmul, mandelbrot, prefix_sum so far) also show what share of that limit each version reached (`bench/run.py --machine` measures again).

It is the first part of 0.4.0: the speed gate's tolerances come from this measured noise.

### Fixed
- **`sort_index` on integers is several times faster:** it boxed every key and compared pairs through the generic comparison; integers (and bytes) are now merged as (key, index) pairs in place, still stable. 2,000,000 keys took about 6 s and now take about 0.7 s, which `graph::bfs`, `graph::topo` and `graph::mst` lean on.
- **`concat` keeps a list's kind, and `push` copies in one go:** `concat` of two lists of the same kind of number gave a list of unknown type to the compiler, so every read of the result went the generic way: 5,000,000 reads of a `concat` result took 2.8 s, 0.02 s now (ChaCha20's block state, built by `concat`: 9.3 s on one core, 3.1 s now). And `push` onto a list still in use copied it one boxed element at a time; it copies the elements in one go now (Catalan numbers by convolution, keeping the list in a local while it grows: 15 s, 2.3 s now).
- **A filter whose mask calls a function runs in parallel:** `xs ⌿ (xs ¨ prime)` was fused into one loop that computed the mask twice (to count, then to fill) on one core; 300,000 Miller-Rabin tests took 1.2 s that way and 0.08 s as a map. Such a filter now builds its mask with `¨`, in parallel; filters on plain arithmetic (`xs ⌿ (xs > 0)`) stay fused.
- **`push` onto bytes grows them in place:** pushing a number onto a `[u8]` list copied the whole list every time (the number did not match the list's kind), so writing bytes one at a time was quadratic: 100,000 pushes took 0.63 s, and LEB128-encoding 4,000,000 numbers did not finish in 10 minutes. A byte pushed onto bytes held once now grows them in place (2 ms for 100,000); a value that is not a byte still turns them into a list of integers, as before.
- **`trail` and `gather` over numbers give numbers:** `xs ▷ trail(+)` (and `×`, `⌈`, `⌊`, and `gather` with them) over a list of `i64` or `f64` was a list of unknown type to the compiler, so every read of the result went through the generic path. A 256-entry table built by `trail(+)` took 3 s to look up 8 million pixels; it takes 0.03 s now. The running results of an empty list of `f64` are an empty list of `f64`.
- **`evolve` and `settle` with functions by name step in place:** `evolve(n, step)` and `settle(step, done)` with named functions called them as function values, which cannot take the state over, so a list in the state was copied at every step: a Bloom filter setting 7,000,000 cells of an 8 MiB list ran for over 15 minutes, and `settle` with a named `done` copied even when the step was a lambda. They are now the same as `s => step(s)` and `s => done(s)`: the Bloom filter takes 0.24 s.
- **A map whose first element is cheap still runs on all cores:** `¨` over up to 16,384 elements that each may be much work (they reach recursion) timed the first element alone and stayed on one core when it was quick. N-queens counted over its 225 first-two-row starts ran on one core because the first start, both queens in one column, costs nothing. It now times 1, 2, 4, 8, … elements and shares out the rest once that is worth waking the threads: 15 queens 4.55 s → 0.53 s on all cores.
- **`and` and `or` decide before running their right side, whatever the types:** where a side's type was known only when the program ran (a parameter without a type, a list from `flatten`), both sides ran first, so `j == ≢ xs or xs[j] > 0` stopped the program reading past the end. The right side now runs only when it decides, as with known truth values; lists still go element by element. Found by a merge sort written for the corpus.
- **`flatten` is fast for small lists too:** making it linear (for many lists) made it slower on few small ones, each a parallel map, a running sum and a replicate: `utf8`, which flattens each character's bytes, ran 7.4 s on one core where 0.3.18 took 5.1 s. Lists that all hold one plain type (numbers, bytes, booleans) are now joined in one copy each: `utf8` 4.1 s (0.58 s on all cores), `rle` 1.8 s (5.4 s before). Found by the speed gate comparing preview.2 with 0.3.18.
- The README of a new project (`mimic create`) links to https://mimic.codes, not the old repository address.
- **A record passed along a recursion is borrowed:** a function that only handed a record on to its own recursive call took it over, so every call from outside retained and released it. Called from every element of a `¨`, all cores wrote the same reference count: `kmeans` with its centres in a record took 11 s on all cores (89 CPU-seconds), now 1.5 s (3.3), the same as with the lists taken out.
- **`put` on a list of bytes is in place:** an integer put into a `[u8]` (or any value whose type differs from the list's) copied the whole list every time, even when nothing else held it. The `sieve` benchmark with byte flags, as C keeps them: 2.9 s on one core (3.6 s with `[i64]` flags, over 2 minutes with bytes before) and 0.35 s on all cores.
- Builds running at once could fail with `redefinition of 'MIM_UI_JS'`: each rewrote the runtime's cached sources while others compiled from them, and the C compiler, which tells files apart by inode, could take one file for another once an inode was reused. The sources of each runtime version are now written once, into a directory moved into place whole.
- **`--preview` picks only a release with files:** the releases feed it reads also lists a tag whose release is still being built, so during the minutes a preview was building, `mimic upgrade --preview` chose it and failed with a 404. It now takes the newest preview or stable release whose files are there.
- **No release without its files:** a release is now published only after its binaries and checksums are uploaded. Before, for a moment a new release could be the latest with nothing to download, and the install command failed with "Not Found" (the install scripts' check on the 0.3.18 release did). That check now runs when the release workflow finishes; it never ran on a release before.
- **Builds at the same time no longer spoil the runtime:** files Mimic writes "atomically" (through a temporary file) used a temporary name per process, so two threads of one build writing the same runtime file shared it and could interleave their bytes; CI saw `redefinition of 'MIM_UI_JS'` once. Every write now has a temporary name of its own, the runtime's object file too.
- **`flatten` is linear:** it joined the lists two at a time, copying the growing result again for every list, so flattening many small lists was quadratic (200,000 pairs: about a minute; now milliseconds). Each element is now placed once, in parallel. The same in the `ui` module. Found by the 0.4.0 benchmark corpus.

### Changed
- **Byte data is fast.** Lists of bytes made by a fused loop are written with SIMD too. Reading an element of a `[u8]` was a call into the runtime that allocated a number (now one load: the scale benchmark went from 10 s to 1.4 s); `bytes::from(…)` over a computed list writes the bytes in one pass, without a list of i64 in between; sums, products, maxima and minima of integer lists run as tight loops. The sum of a `[u8]` is an `i64` (it was typed as a list, which sent the code around it to slow paths).
- **Loops whose elements are big pieces of work use every core**: `⍳ 30 ¨ frame` where each `frame` works over a million pixels ran on one core, as 30 elements looked small. An element whose function itself loops over arrays is now timed and shared out (2 → 6 of 12 cores in the scale benchmark).
- **The function a fused `¨` applies goes inside the loop** (inlined), so its checks that do not depend on the element (divisors, the lists' headers) leave the loop.
- **Integer `div` and `%` of numbers that are not negative take a plain divide**, without the correction that rounding towards minus infinity needs (the results are the same); LLVM drops or hoists the test where it can. The transcode example's scaler: 8.8 s → 6.4 s on one core. (Replacing a divide by a precomputed reciprocal, as C compilers do for constant divisors, was tried for divisors fixed in a loop: slower on both Apple's arm64 cores and AMD's x86 ones, whose dividers are fast; left out.)
- **`let (a, b) = …` of numbers stays in registers**, from a tuple or an `if` whose branches are tuples: in a loop over pixels it made, checked and released a tuple per pixel (the transcode example's scaler: 116 s → 0.9 s).

- **State machines change their lists in place.** `{ s with xs: push(s.xs, x) }`, `concat` and `put` (and chains such as `put(put(s.xs, i, a), j, b)`) take the list out of a record held once and change it there, growing it with room to spare, instead of copying it each time; a list still held elsewhere is copied as before, so results never change. `settle` and `evolve` hand their state to each step (a record held once), `settle` with a typed step is a compiled loop (it went through the runtime), and a function takes its record parameter over when each `with` on it, or a call it is passed to, is its result on that path. Dijkstra with a heap on a 600×600 grid went from not finishing in 10 minutes to 0.4 s; a QOI encoder from hours to 1.4 s.
- **Small pure helpers stay native.** A pure function making several calls at once (`slot(p)` calling `red`, `green`, `blue`) went to the interaction nets even without any recursion in reach, where each call cost thread wake-ups; the nets are kept for work that can grow.
- **Lists of up to 16 numbers stay in registers** (it was 8): a 3×3 neighbourhood or a 4×4 matrix allocates nothing. `sort` of such a list sorts on the stack; `sort(⍳ 9 ¨ f)[4]` (a median) allocates nothing; the runtime sorts lists of up to 64 numbers with an insertion sort (the radix sort allocated and cleared buffers). The median filter: 5.5× → 1.6× C on one core, on par with Rust + Rayon on all cores.

### Fixed
- **A fused loop shared out over the cores could compute wrong numbers and crash** when it used a list or a record small enough to be kept in registers (`nbody`'s bodies): such a value is wider than one slot of the kernel's context and overwrote the next ones. It now goes by address. (Found when today's change sent more loops down that path; a small constant loop like `⍳ 5` is not counted as heavy work.)
- **`panic` and `os::exit` take no part in a value's type**: `match fs::read_bytes(p) { Ok(b) => b, Err(e) => panic(…) }` was dynamic (the arms joined bytes with nothing), so everything computed from it ran on slow paths; it is `[u8]`.

- **`mimic lsp`, the language server** (step 0.3.4): errors as you type with the compiler's fixes as quick fixes; hover with signature, comment and effects (for C functions, their header; for glyphs and their words, what they do and how to type them); go to definition and find references, into the standard library; glyph input (`\i` → `⍳`) and completion of names, modules, words and keywords; formatting in the style the file mostly uses; the outline and workspace symbols; names from C as semantic tokens with the modifier `foreign`. Set-up for VS Code, Neovim, Helix, Emacs, Sublime Text and Zed: `mimic man editors`.

- **The VS Code extension** (step 0.3.5), in the new [mimic-vscode](https://github.com/mimiccodes/mimic-vscode) repository (a submodule at `editors/vscode`): everything of `mimic lsp`, the highlighting and file icon, a glyph palette, **Run** and **Run test** above functions and tests, the Test Explorer (tests and examples in comments, with both sides of a failed `expect`), the manual beside the code, conversion between glyphs and words, and a check that `mimic` is new enough. CI runs it in a real VS Code against the `mimic` it builds.

- **Debugging shows Mimic's values** (step 0.3.6). `mimic lldb` shows text, lists, maps (`["a": 1, "b": 2]`), records (also those kept in registers, which had no debug information before: `Point { x: 1.5, y: 2.0 }`), lists of numbers as `[3 1 4]` and variants as `Some(7)`, without the handles' addresses. `mimic dap` debugs from editors over the Debug Adapter Protocol (through LLVM's `lldb-dap`): breakpoints on `.mim` lines, stepping, the call stack, and the same values; in VS Code, F5 or **Debug** above `fn main`.

- **`mimic mcp`, Mimic for AI agents** (step 0.3.7), over the Model Context Protocol: tools to check (every error with its exact fixes, as JSON), build, run (with input and a timeout), test, format, explain errors, read the manual and search it, look up symbols and effects, and read and write the project's files; resources (the guide for agents, the glyph table, every page of the manual) and prompts (write Mimic, port code to Mimic, fix the errors). Full access inside the project; outside it, files (`--allow-outside`), installing (`--allow-install`) and running programs that use the network or run other programs (`--allow-network`) stay off until allowed; `--read-only` and `--no-run` narrow it. Set-up for VS Code, Cursor, Windsurf, Zed, Codex CLI and any MCP app: `mimic man mcp`.

- **Documentation written by people or agents** (step 0.3.8). Guides, Markdown pages in the project's `docs/` folder, join `mimic doc` beside the API; their `mimic run` examples run under `mimic test` against their `output` blocks. The site is new: guides and modules in the sidebar, Mimic code coloured, every glyph explained on hover, Mimic's colours in light and dark; `mimic doc --std` includes the manual's guides. Through `mimic mcp`, agents see what is undocumented (`docs_status`), write guides whose examples are checked as they are written (`docs_write`), and build the site (`docs_build`); the `document_project` prompt starts the job.

- **Where code runs** (step 0.3.9). `mimic why` lists every decision the compiler makes about a program or one function: `¨` on all cores, fork-join recursion, interaction nets, fused loops, SIMD, the GPU, implicit tasks, effects kept in order and the places that wait for tasks, each with its reason and what would change it. Code generation records these decisions as it makes them, and `mimic why` reads them from a compile that stops before LLVM optimises. Editors show them as labels after the code (`∥ parallel`, `⇶ fused`, `▣ GPU`, `◷ task`, `→ in order`) with the reason on hover, and agents ask with the `why` tool of `mimic mcp`.

- **`mimic audit`** (step 0.3.10): quality rules (unused functions and variables, dropped `Result`s, long, complex and duplicated functions, C functions that could be `pure`, `trusted` C functions taking pointers) and security rules (`os::shell` with commands built from data, files opened with paths from HTTP requests, secrets in source, certificate trust outside tests, `unsafe` blocks, trusted headers, dependencies following a branch), each with a manual page (`mimic man S01`). Reports as text, JSON or SARIF; `--fail-on` makes it a gate for CI (errors by default); a baseline counts only new findings; each run's counts are kept and compared. Agents get it as the `audit` tool, and CI audits the examples.

- **Contracts and property tests** (step 0.3.11). `requires` and `ensures` lines before a function's body (`result` is the value returned) are checked on every call in debug builds and tests, also when the body leaves with `return`, and left out of release builds; a broken one stops with the condition, the function and the line, and they show in signatures (hover, `mimic doc`). `test "…" for xs: [i64] { … }` runs the body for 100 generated inputs (`i64`, `f64`, `bool`, `str` and lists of them), the same on every run, and shrinks a failure to its smallest case. Both grammars know `requires`, `ensures` and `for`.

- **`mimic repl`** (step 0.3.13): Mimic a line at a time. An expression shows its value, a `let` keeps it, a `fn` or `type` stays defined, and an open bracket continues on the next line. Glyph input as you type (`\i` → `⍳`) and history with Up and Down; `:show` prints the session as a program, `:reset`, `:man`, `:glyphs`, `:quit`. Every line is compiled to native code and run; a line that does not compile shows its errors and is not kept. In `mimic edit`, the same REPL is a pane: F4 evaluates a line you type, Ctrl-E the current line or the selection.

- **The language server finds its way around**: signature help, rename (the program's own names), the call hierarchy (who calls a function, what it calls), smart selection, the inferred type of each `let` as an inlay hint with a code action that writes it in, and *Extract into a function*. `mimic query types` gives those types to other tools.
- **`mimic profile --for SECONDS`**: profiles a server (or any program that does not end by itself) for that long, timed by the program. Servers are profiled properly: the event loop's threads and the tasks on them are sampled, and waiting for the network, for work or in `time::sleep` counts as waiting.
- **Targets:** `aarch64-windows` is stable (CI runs every golden program on a Windows arm64 machine).
- **`mimic test --coverage`**: how often the tests ran each line of the program's own code, lines of functions nobody called included: a summary per file with the lines not run, `coverage.json` for editors (the VS Code extension's Coverage run) and `lcov.info` for coverage services.
- **`mimic repl --json`**: requests and answers as JSON lines, for notebooks and tools (the VS Code extension's `.mimnb` notebooks).
- **Windows**: the language server compared Windows paths in their `\\?\` form with the paths editors send, so errors and lookups could miss open files; paths are now compared and reported as editors write them. A test of the language server that hung for two hours on Windows CI (it waited for an answer to a malformed path) now finishes, and any test talking to a server stops it after three minutes without an answer.
- **`mimic net show` and `mimic net trace`**: the interaction nets of a program's pure functions (or of a `.mnet` file) as text or as graphs (`--json`: nodes, ports, wires, active pairs), also as compiled before compile-time reduction (`--before`); and a call reduced round by round with the runtime's rules, giving the result, the interactions, the redexes of each round (the parallelism the net offers) and the rules that fired, with the net before each round for drawing (`--frames`). The VS Code extension draws and plays them.
- **The VS Code extension 0.4–0.10**: finds Mimic by itself (VS Code started from the Dock does not see the PATH of `~/.zshrc`, so it asked for `mimic.path`), installs and updates it from GitHub, shows errors on save with a Mimic without the language server, profiles (a panel, shares in the code, hot functions), lists where code runs, runs the REPL, and shows and traces interaction nets.
- **`mimic profile`** (step 0.3.13): runs the program and shows where its time goes: the share per function (self, and with what it calls) beside where the compiler runs it, the runtime and system functions that took it, each thread's share of time working, GPU kernels and their time, and memory allocated and copied. The runtime samples every thread about 1000 times a second (signals on Linux and macOS, suspending the thread on Windows) and follows the frame pointers a profiling build keeps; time on the pool's workers counts for the function that started the loop. The report is saved as JSON; `--json` prints it, and `mimic mcp` has a `profile` tool. `mimic man profile` explains it.
- **Tail-recursive loops stay native.** A pure function whose calls are all in different branches (a loop written as tail recursion) no longer runs on the interaction nets, where it gained nothing: it compiles to a loop, as fast as the same loop in C (a 400-million-step loop: 20 s on the nets on 8 cores' worth of CPU, now 10 s on one core, like C). Found with `mimic profile`.
- Fused kernels are named after the function they come from (`…main__f$i$kernel3`), in profiles and debuggers.

- **Rust + Rayon in the benchmarks** (step 0.3.13): `bench/<name>/rayon/` is the hand-parallelised Rust version of seven benchmarks, timed on all cores next to Mimic on all cores in `bench/run.py`, `BENCHMARK.md` and the weekly CI run. Cargo projects in the suite now build with `-C target-cpu=native`, as the single-file Rust versions do. Mimic is ahead on six of eight with no annotations; Rayon is ahead on prefix sum and fib.

- **`mimic edit`, Mimic's own terminal editor** (step 0.3.12): in Mimic's colours, with a MIMIC start screen; highlighting from Mimic's own lexer (names from C in their own colour); glyph input (`\i` → `⍳`, never inside strings) and a glyph palette; errors as you type from the engine (a mark, the code underlined, the message); panes for problems, the audit, where code runs (also as labels beside the code), the manual for the word under the cursor, and run and test output (in the background); tabs, a file tree, a fuzzy file opener, find and replace, undo and redo, the clipboard, the mouse, indentation that follows the code. Easy keys: Ctrl-S, Ctrl-Q (asking about unsaved files), Ctrl-O, Ctrl-G, F1, F5, F6.

### Changed
- **`mimic check` is about 2.5× faster** (the showcase: 90 ms → 35 ms of analysis). Name lookups are remembered once the module tree is built, and names that turn out to be local variables no longer run the "did you mean" search, which only an error needs.

## 0.2.9 — 2026-11-15

Stage 0.2 complete: native windows on Windows and Linux, shared libraries, thousands of waiting tasks on the event loop, terminal programs, text formats, collections, C constants, globals, structs and unions, and Windows at full speed.

**Upgrading from 0.2.0:** names from C are now written with `c::` (`c::printf`, `c::sqrt`). Run `mimic check --fix` in each project to add it where it is missing. The install script replaces the old `mimic` and clears its build cache.

### Changed (breaking)
- **Everything from C is written with the namespace `c::`:** `c::printf(…)`, `c::sqrt(2.0)`, `c::Vec2 { … }`, for functions from `extern "C"` blocks, imported headers and C struct records alike. It is required, so C code is always visible, and C names never collide with Mimic's (`c::abs` next to `abs`, `c::div` next to the `div` operator). `extern "C" include "sqlite3.h" as sql` picks another namespace. A C name used without it is error E0303 with the fix (`did you mean c::floor?`). C++ will use `cpp::`. To update code: put `c::` before each C function and struct name.

### Fixed
- **Windows programs run at full speed.** Native Windows builds compiled for the plain x86-64 baseline (no AVX2, no FMA), because the MinGW host triple picked up Clang's cross-compiling defaults; they now use the machine's own CPU, as on macOS and Linux. On a Zen 3 runner: `mandelbrot` 1.14× → 0.76× C on one core, `sum_of_squares` 4.1× → 1.1×. CI now checks which CPU Windows code generation used.
- Windows: idle worker threads napped with `Sleep(0)`, which returns at once, so they spun on the cores the working threads needed; they now sleep 20 µs on a high-resolution timer (`fib` on all cores 0.89× → 0.68× C).
- Parallel prefix sums (`trail`) were slower on several threads than on one on Windows: scans now work in larger chunks (Windows 1.46× → 0.84× C on 4 threads; macOS and Linux a little faster too).
- A rare hang on Windows: two tasks using one socket (a WebSocket's reader and writer) could switch its non-blocking mode under each other, and a read then blocked a whole event-loop thread. Sockets used by tasks now stay non-blocking.
- A coroutine's lock could be freed while the thread finishing it was still releasing it (harmless with glibc, not with Windows' threads library).
- `time::format`'s message for an unknown pattern code was cut off.
- `bench/run.py` writes its results as UTF-8 on Windows.
- Tests: `http_keep_alive` takes its port below the ones the OS hands out (it could race with a parallel test); `c_struct_pointers` uses `termios.h` only on Unix.
- `"\033"` and other C octal escapes were read as NUL followed by digits, silently; they are now an error that suggests `\x1b`.
- Importing a C header failed when it declared a name Mimic uses itself (`div` in `stdlib.h`, a field `type`, a function `sum`). Under `c::` (below) they keep their C spelling; a wrapper that cannot be written in Mimic is left out instead of failing the import.

### Added
- `MIMIC_DEBUG_WATCHDOG=<seconds>`: a program still running after that long prints every task and what it waits for (a channel, a join, a socket, a timer), to find hangs. `MIMIC_DEBUG_CPU=1` prints the CPU code generation chose. `tools/speed-probe.py` and the manual "speed probe" workflow time benchmarks against C by thread count on CI machines.
- Native windows on Windows and Linux: `ui::run(…, show: "window")` (`mimic run --window`) uses Win32 controls on Windows and GTK 3 on Linux (loaded when the window opens, so programs do not depend on it), as AppKit on macOS. The same window test runs on all three in CI, Linux under a virtual display.
- Shared libraries: `mimic build --shared` builds a library project as `lib<name>.dylib`, `lib<name>.so` or `<name>.dll` (with the import library `lib<name>.dll.a`), exporting only its `extern "C" fn`s, for any language that calls C. Cross builds too (`--target x86_64-windows`).
- `¨` over a function that waits on the network or sleeps runs every element as a task on the event loop instead of a core's worth at a time: 3000 WebSocket clients each holding a connection for half a second finish in about a second (was two minutes). Programs raise their open-file limit at start, so thousands of sockets fit.
- Speed checked on Windows: CI counts AVX2/AVX-512 instructions in a native Windows build of the SIMD fixture, and the benchmark workflow runs on Windows too (`bench/run.py` works there).
- C unions: a record with one field per member (`c::Num { f: 2.5 }`), by value, in structs and through pointers; the member set is the one C sees.
- C structs: array fields are lists; `c::T { … }` leaves fields out as zero (`c::Termios {}`); plain-data structs through pointers are records (`const`: copied in; otherwise copied in and returned, in a tuple with the result), so `c::tcgetattr(0, c::Termios {})` works. Records exist for every C struct the code names.
- `mimic check --fix` adds a missing `c::` (functions and constants).
- C constants and globals: `#define` constants and enum values (`c::SEEK_END`, `c::M_PI`, `c::TIOCGWINSZ`), computed by Clang and inlined; globals and expression macros (`c::stdout`, `c::errno`) read through generated getters; `#define` aliases of functions (`c::CreateFile`); C functions with uppercase names (the Windows API). Struct, callback and getter wrappers are generated only for the C names a program uses.
- Collections: `unique`, `sort_by` (stable, `descending: true`), `zip`, `enumerate`, `any`, `all`, `count`, `group_by`, `flatten`, `min_by`, `max_by`, `clamp`, `to_map`, and a `set` module (`set::of`, `has`, `add`, `remove`, `union`, `intersection`, `difference`).
- `panic(message)` and `assert(ok, message)` in ordinary code; `os::env_all()`; `fs::walk(dir)` and `fs::modified(path)`; `time::format(t, pattern)` (`%Y-%m-%d %H:%M`); `random::choice` and `random::shuffle`.
- Terminal programs without C: `io::write` (no newline), `io::flush`, `io::read_char`, `io::read_bytes`; the `term` module (`raw`, `read_key`, `size`, `is_terminal`, `clear`, `move_to`, `show_cursor`, `alternate_screen`, undone when the program ends), on Windows too (ANSI codes are switched on); `os::on_interrupt` for Ctrl-C.
- Formats in interpolation, as in Python and Rust: `"{x:.2}"`, `"{n:>8}"`, `"{n:06}"`, `"{n:#x}"`, `"{n:,}"`, `"{x:.1%}"`; `format(x, spec)`. A bad format is a compile error.
- `char_code`, `char_of`, `pad_start`, `pad_end`, `words`, `slice`, `parse_int(text, base)`.
- `docs/gaps.md` and `tools/gaps.sh`: everyday features checked against the compiler, each with the version that closes it.
- String escapes `\x1b` (an ASCII character by two hex digits) and `\u{1F600}` (any Unicode character), so terminal colour and cursor codes can be written.
- TLS in static Linux programs: `https://` and `tls::` work in `--target x86_64-linux` (and every other `*-linux-musl`) builds, through Mbed TLS 3.6 bundled in `mimic` and built for the target on first use. They trust the system's CA bundle, or `SSL_CERT_FILE`.
- The Linux `mimic` is built against glibc 2.28, so it runs on Linux systems from 2018 on (Ubuntu 20.04, Debian 10, RHEL 8 and later).
- `NOTICE` lists the software bundled in `mimic`; release downloads include it.
- The event loop on Windows: connections and the tasks they start run as coroutines (fibers), waiting on sockets through IOCP (wepoll) instead of a thread each, as on macOS and Linux.
